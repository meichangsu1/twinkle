# Multi-LoRA Async RL 实验计划与指标采集手册

## 1. 实验目标

本实验验证 Multi-LoRA Async RL 相比 Multi-LoRA 同步 RL 的优势，分两个层面：

1. 效率层面：验证 async RL 是否能通过跨 LoRA 的 rollout/train 重叠提升 wall-clock 训练效率。
2. 效果层面：验证 async RL 在 strict on-policy 条件下是否能接近同步 RL 效果，并观察 relaxed staleness 下的效率/效果 tradeoff。

核心假设：

```text
同步 RL:
  LoRA1 rollout -> LoRA2 rollout -> barrier -> LoRA1 train -> LoRA2 train -> barrier

异步 RL:
  LoRA1 train 的同时，LoRA2 可以 rollout
```

async RL 的主要收益不是让单个 LoRA 更 off-policy，而是让不同 LoRA 的 rollout/train 阶段重叠，减少 sampler/trainer 空转。

## 2. 实验设置

首轮实验使用当前配置：

```text
config: cookbook/rl/async_multi_lora_grpo.yaml
dataset: GSM8K
num_loras: 2
reward: GSM8K accuracy + brevity
algorithm: GRPO
```

每组实验固定以下变量：

```text
模型版本
数据集 split / data_num
LoRA rank
optimizer
num_generations
sampler 参数
GPU 拓扑
max_steps
随机种子
```

每组实验至少跑 3 个 seed，报告 mean/std。

首轮主实验使用公平粒度：

```text
每个 LoRA 的 rollout.batch_size 相同
每个 LoRA 的 train.mini_batch_size 相同
rollout_policy = weighted_fair
train_policy = weighted_fair
```

这样比较的是 async 调度是否能让不同 LoRA 的 rollout/train 重叠，而不是比较不同 LoRA batch 粒度或调度偏置带来的差异。

## 3. 对比组

主实验三组：

```text
A. sync_barrier
   Multi-LoRA 同步 baseline。
   所有 LoRA 完成 rollout 后统一 train。
   不允许 rollout/train 跨阶段重叠。

B. async_strict
   Multi-LoRA Async RL。
   max_staleness = 0。
   目标：效果接近 sync_barrier，同时 wall-clock 更快。

C. async_relaxed
   Multi-LoRA Async RL。
   max_staleness = 1。
   目标：观察更高吞吐和 policy staleness 对效果的影响。
```

可选 sanity 组：

```text
D. single_lora_sync
E. single_lora_async
```

用于证明主要收益来自 multi-LoRA overlap。

## 4. 运行流程

同步 baseline 采用阶段 barrier：

```text
for round in training:
  for each LoRA:
    保存当前 adapter
    使用当前 adapter rollout
  barrier

  for each LoRA:
    计算 reward
    计算 advantage
    train mini-batches
    保存 / 同步 adapter
  barrier
```

要求：

```text
同一轮 train 只能使用本轮 rollout 数据
不允许 LoRA1 train 时 LoRA2 同时 rollout
所有 LoRA 完成当前阶段后才能进入下一阶段
```

执行示例：

```bash
python cookbook/rl/sync_barrier_multi_lora_grpo.py \
  --config outputs/async_rl_experiments/sync_barrier_seed0/config.yaml
```

async strict 使用现有 pipeline：

```text
PromptLoader -> AsyncRollouter -> TQ -> AdvantageWorker -> TrainerWorker
```

配置：

```yaml
pipeline:
  max_staleness: 0
```

要求：

```text
policy_version_gap_mean == 0
stale_drop_ratio == 0
```

async relaxed 配置：

```yaml
pipeline:
  max_staleness: 1
```

目标是观察吞吐是否继续提升、policy_version_gap 是否增大、reward/accuracy 是否下降，以及 reward vs wall-clock 是否仍然更优。

## 9. 成功标准

`async_strict` 相比 `sync_barrier`：

```text
reward / accuracy 在相同 train step 下相对差距 <= 5%
train_partitions_per_hour >= 1.2x
overlap_ratio > 0.3
policy_version_gap_mean == 0
stale_drop_ratio == 0
每个 context 都持续推进，无 starvation
```

`async_relaxed`：

```text
效率高于 async_strict
明确报告 staleness 增幅
如果效果下降，需要通过 reward vs wall-clock 判断 tradeoff 是否值得
```
